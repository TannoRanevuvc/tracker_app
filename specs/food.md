# Спека модуля: food

## 1. Назначение

Фуд-трекер: расчёт КБЖУ по приёмам пищи (аналог FatSecret/Yazio). MVP — ручной ввод
типовых продуктов; поиск через Open Food Facts — вторым шагом внутри модуля (см. §2).

## 2. Границы (Scope)

**Входит в модуль (MVP, этап 1):**
- Ручной ввод продуктов пользователя (название + КБЖУ на 100г)
- Логирование приёмов пищи с указанием продукта и веса порции
- Расчёт дневного итога КБЖУ и сравнение с целью
- Опциональная цена приёма пищи → событие для `finance`

**Входит в модуль (этап 2, после MVP):**
- Поиск продуктов через Open Food Facts API по названию/штрихкоду с локальным кэшем

**Явно НЕ входит (Out of scope):**
- Готовые рецепты/блюда из нескольких ингредиентов (в MVP — один продукт = один пункт
  приёма пищи; блюдо из нескольких продуктов логируется как несколько записей)
- Сканирование штрихкода камерой на этом этапе (фронтенд-фича, не блокирует бэкенд-спеку)
- Социальные функции (шеринг дневников, сравнение с другими)

## 4. API-контракт

| Метод | Путь | Запрос | Ответ | Коды |
|---|---|---|---|---|
| POST | /api/food/products | `{name, kcal_per_100g, protein_g_per_100g, fat_g_per_100g, carbs_g_per_100g}` | `Product` | 201, 422 |
| GET | /api/food/products | query: `q?` (поиск по имени, локальный кэш + свои) | `Product[]` | 200 |
| POST | /api/food/meal-entries | `{product_id, quantity_g, meal_type, logged_at?, price_kopecks?}` | `MealEntry` (с рассчитанными абсолютными КБЖУ) | 201, 404, 422 |
| GET | /api/food/meal-entries | query: `date` | `MealEntry[]` | 200 |
| DELETE | /api/food/meal-entries/{id} | — | — | 204, 404 |
| GET | /api/food/summary | query: `date` | `{kcal_total, protein_total, fat_total, carbs_total, kcal_goal, goal_reached}` | 200 |
| POST | /api/food/goals | `{kcal_goal, protein_goal_g?, fat_goal_g?, carbs_goal_g?, effective_from}` | `DailyGoal` | 201, 422 |
| GET | /api/food/goals/current | — | `DailyGoal` | 200, 404 (цель не задана) |

Этап 2 (после MVP на ручном вводе):

| Метод | Путь | Запрос | Ответ | Коды |
|---|---|---|---|---|
| GET | /api/food/products/search-external | query: `q` | `ExternalProductPreview[]` (из Open Food Facts, не сохранены — без `id`, см. примечание ниже) | 200 |
| POST | /api/food/products/import-external | `{external_id}` | `Product` (сохранён в локальный кэш; если `external_id` уже был импортирован ранее — возвращается существующая запись, см. §6) | 200 (уже был закэширован), 201 (сохранён впервые), 404 (не найден во внешнем API) |

**`ExternalProductPreview`** — отдельная, более лёгкая схема ответа для
`search-external`: `{external_id, name, kcal_per_100g, protein_g_per_100g,
fat_g_per_100g, carbs_g_per_100g}`, без `id` — продукт ещё не в БД, `id` (UUID PK)
физически не существует до вызова `import-external`. Не путать с `Product` — это разные
Pydantic-схемы, `ExternalProductPreview` не может использоваться там, где ожидается
`Product` (например, как `product_id` в `POST /meal-entries`).

## 5. События

**PUBLISHES:**

| Событие | Когда | Payload |
|---|---|---|
| `food.meal_logged` | после создания приёма пищи | `{meal_entry_id, user_id, date, kcal, price_kopecks}` (`price_kopecks` может быть `null`) |
| `food.daily_goal_reached` | когда дневной итог kcal впервые за день достигает или превышает `kcal_goal` | `{user_id, date, kcal_total, kcal_goal}` |

**SUBSCRIBES_TO:** нет.

## 6. Бизнес-правила и edge cases

- **Расчёт абсолютных КБЖУ приёма пищи:** `quantity_g / 100 * {kcal,protein,fat,carbs}_per_100g`
  продукта, округление до 1 знака после запятой. Хранится денормализованно в `meal_entry`
  на момент создания (если продукт потом отредактирован — исторические записи не
  пересчитываются, чтобы дневник за прошлые дни не "плавал").
- **`food.daily_goal_reached` — публикуется один раз в день**, при первом запросе, где
  сумма kcal ≥ цели (дедупликация по `user_id + date` в обработчике, аналогично
  дедупликации `task.overdue`).
- **Активная цель** — та, у которой `effective_from <= сегодня`, максимальная среди
  таких по `effective_from` (последняя заданная).
- **`price_kopecks` необязателен** — если не указан, событие `food.meal_logged` уходит
  с `price_kopecks: null`, `finance` его игнорирует (см. спеку `finance.md` §5).
- **Поиск продуктов (`GET /products`)** в MVP ищет только среди уже существующих в БД
  записей (свои + ранее закэшированные) — без обращения к внешнему API. Внешний поиск —
  отдельный эндпоинт этапа 2, осознанно не смешивается с основным поиском, чтобы не
  блокировать ответ на медленный внешний вызов.
- **Идемпотентность `import-external` (этап 2):** `external_id` уникален среди продуктов
  в `food.product`. Если запрошен `external_id`, который уже был импортирован ранее,
  дубликат не создаётся — возвращается существующая запись с кодом 200 (не 201). Иначе
  один и тот же внешний продукт мог бы задублироваться в локальном поиске.
- **Недоступность Open Food Facts (этап 2):** вызов к внешнему API — с таймаутом; при
  недоступности `search-external` возвращает пустой список или 502 (не должно ронять
  остальной функционал модуля), `import-external` — 502, а не 404 (404 зарезервирован
  за случаем "внешний API ответил, но такого `external_id` у него нет").

## 7. Критерии приёмки

1. **Given** продукт "Гречка" с `kcal_per_100g: 110`, **When** POST приёма пищи
   `quantity_g: 200`, **Then** в ответе `kcal = 220.0`, публикуется `food.meal_logged`.
2. **Given** дневная цель `kcal_goal: 2000`, уже залогировано 1900 kcal сегодня,
   **When** логируется приём пищи на 150 kcal, **Then** публикуется
   `food.daily_goal_reached` с `kcal_total: 2050`.
3. **Given** цель уже достигнута сегодня и событие уже опубликовано, **When**
   логируется ещё один приём пищи в тот же день, **Then** `food.daily_goal_reached`
   повторно не публикуется.
4. **Given** приём пищи без `price_kopecks`, **When** он создаётся, **Then**
   `food.meal_logged` публикуется с `price_kopecks: null`.
5. **Given** продукт отредактирован (изменены КБЖУ на 100г) после того, как приём пищи
   уже залогирован, **When** GET старой записи `meal_entry`, **Then** абсолютные КБЖУ
   в ней остаются прежними (не пересчитываются от нового значения продукта).
6. **Given** заданы две цели с разными `effective_from` (одна в прошлом, одна с завтра),
   **When** GET `/goals/current` сегодня, **Then** возвращается цель с `effective_from`
   в прошлом (более поздняя ещё не вступила в силу).
7. **Given** запрос `GET /api/food/products?q=греч`, **When** есть сохранённый продукт
   "Гречка", **Then** он находится без обращения к внешнему API.

## 8. Нефункциональные заметки

- MVP: 20–30 продуктов вручную — объём тривиальный, полнотекстовый поиск не нужен,
  достаточно `ILIKE '%query%'` по имени.
- Этап 2 (Open Food Facts): внешний вызов — с таймаутом и явной обработкой недоступности
  API (не должно ронять остальной функционал модуля).

## 9. Открытые вопросы

- Нужны ли "блюда" как отдельная сущность (сохранённый набор продуктов с весами,
  логируемый одним действием) — отложено до накопления раздражения от ручного
  повторения одних и тех же комбинаций.
- Момент и способ интеграции с Open Food Facts (авто-подстановка при поиске vs
  отдельная кнопка "искать во внешней базе") — уточнить перед этапом 2.
