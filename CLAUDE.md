# CLAUDE.md — Персональное модульное приложение

## 1. Видение

Личное веб-приложение для управления собственной жизнью: задачи, финансы, привычки,
питание (КБЖУ) и мотивационный слой поверх всего этого. Не продукт для рынка — инструмент
для одного пользователя (себя), без дедлайнов, без требований к монетизации или
масштабированию на других людей.

Ключевое архитектурное требование: **модульность**. Новые направления (модули) должны
добавляться без переписывания существующего кода — как бэкенда, так и фронтенда. Модуль
может быть выключен, удалён или добавлен независимо от остальных.

Нефункциональные приоритеты (в порядке важности для личного проекта):
1. Лёгкость добавления нового модуля
2. Простота эксплуатации (один сервер, минимум движущихся частей)
3. Удобство использования с телефона наравне с десктопом (PWA)
4. Разумная безопасность (личные финансовые и пищевые данные — не для публичного доступа)

## 2. Архитектурный принцип: модульный монолит

Не микросервисы. Один процесс FastAPI, один процесс React SPA, одна база Postgres —
но с жёсткими внутренними границами между модулями:

- Каждый модуль — своя папка в бэкенде и своя папка во фронтенде
- Каждый модуль — своя схема (`SCHEMA`) в Postgres
- Модули **не импортируют код друг друга напрямую**
- Модули общаются только через событийную шину (см. раздел 7)
- Ядро (`core`) не знает о существовании конкретных модулей — только о их реестре

Критерий "правильной" модульности: модуль `food` можно физически удалить (папку бэкенда,
папку фронтенда, `DROP SCHEMA food`) — и всё остальное приложение продолжит работать без
единой правки кода в других модулях.

## 3. Технологический стек

**Бэкенд**
- Python 3.12, FastAPI
- SQLAlchemy 2.0 (async) + Alembic (отдельная ветка миграций на модуль)
- Pydantic v2 — схемы запросов/ответов
- PostgreSQL — отдельная схема БД на модуль
- JWT в httpOnly cookies, bcrypt (cost 12) — по твоей стандартной конвенции безопасности
- Событийная шина: `asyncio`-based in-process pub/sub на старте, без внешних очередей

**Фронтенд**
- React + Vite (не Next.js — SSR/SEO не нужны для личного приложения за авторизацией)
- TypeScript
- Tailwind CSS + shadcn/ui
- TanStack Query — работа с API, кэширование
- TanStack Router (или React Router) — роутинг с namespace на модуль
- `vite-plugin-pwa` — PWA-обёртка

**Инфраструктура**
- Docker Compose (backend, frontend build, Postgres, Nginx)
- Nginx — реверс-прокси, раздача статики фронтенда, TLS
- Деплой на своём VPS (соответствует остальной твоей инфраструктурной практике)

## 5. Контракт модуля

Чтобы добавление модуля было механическим действием, а не архитектурным решением каждый раз,
каждый модуль обязан предоставить:

**Бэкенд:**
- `router: APIRouter` с префиксом `/api/{module_name}` — единственная точка входа модуля
- `models.py` с `__table_args__ = {"schema": "{module_name}"}` на каждой модели
- собственная ветка Alembic-миграций, не зависящая от миграций других модулей
- `events.py` с двумя списками: `PUBLISHES` (какие события модуль публикует) и
  `SUBSCRIBES_TO` (на какие события модуль подписывается, с указанием обработчика)
- регистрация в `main.py` одной строкой: `app.include_router(module.router)`

**Фронтенд:**
- `routes.tsx`, экспортирующий роуты модуля под `/{module_name}/*`
- пункт в общем меню навигации (конфиг, не хардкод в компоненте шелла)
- собственные TanStack Query хуки, обращающиеся только к `/api/{module_name}/*`

Ядро никогда не редактируется при добавлении нового модуля — только точка регистрации.

## 6. Ядро (Core)

- **Auth** — единая аутентификация для всех модулей (раз пользователь один — можно даже
  без полноценной ролевой модели, но JWT + httpOnly cookies оставляем для унификации и на
  случай, если позже подключишь второго пользователя, например партнёра)
- **Event bus** — общая шина, независимая от модулей
- **Module registry** — список активных модулей с метаданными (имя, версия, включён/выключен);
  можно хранить как простой Python-список в конфиге на первом этапе, без БД-таблицы
- **Shell (фронт)** — общая навигация, тема, layout — не знает, что за модули будут внутри

## 7. Событийная шина

Модули не вызывают друг друга напрямую. Пример потока:

```
habits.completed  →  event bus  →  tasks (подписан: создать задачу "внести вес")
                                →  motivation (подписан: начислить XP, обновить стрик)
```

Реализация на старте — простая, без внешних зависимостей:

```python
# core/events/bus.py
class EventBus:
    def __init__(self):
        self._subscribers: dict[str, list[Callable]] = defaultdict(list)

    def subscribe(self, event_name: str, handler: Callable):
        self._subscribers[event_name].append(handler)

    async def publish(self, event_name: str, payload: dict):
        for handler in self._subscribers[event_name]:
            await handler(payload)
```

При регистрации модуля в `main.py` его `events.SUBSCRIBES_TO` прогоняется через
`bus.subscribe(...)`. Если позже понадобится персистентность (аудит, replay, обработка
в фоне) — добавляется таблица `event_log` в схеме `core` и/или Redis pub/sub, но это
не нужно на старте.

## 8. Модули

### 8.1 Tasks (таск-трекер)
- Данные: задачи (заголовок, описание, статус, дедлайн, приоритет, привязка к проекту/тегу)
- Публикует: `task.completed`, `task.overdue`
- Подписан на: `habit.completed` (опционально — автосоздание задачи по привычке)

### 8.2 Habits (хабит-трекер)
- Данные: привычка (название, частота — ежедневно/по дням недели), отметки выполнения по дням,
  текущий стрик
- Публикует: `habit.completed`, `habit.streak_broken`
- Простейший модуль по модели данных — рекомендуется первым в реализации

### 8.3 Finance (финансовый трекер)
- Данные: транзакции (сумма в копейках — integer, никогда float), категории, регулярные операции,
  балансы по счетам
- Публикует: `finance.transaction_added`, `finance.budget_exceeded`
- Подписан на: `food.meal_logged` (опционально — авторасчёт трат на еду, если укажешь цену)

### 8.4 Food (фуд-трекер, КБЖУ)
- Самый тяжёлый модуль по объёму данных. Рекомендации:
  - **Не строить свою базу продуктов с нуля.** Использовать Open Food Facts API
    (бесплатный, открытый) для поиска и получения КБЖУ по штрихкоду/названию,
    с локальным кэшем часто используемых продуктов в своей БД
  - На старте MVP — ручной ввод 20–30 своих типовых продуктов/блюд вместо полноценного
    поиска, чтобы не блокировать запуск остальной части приложения
- Данные: продукты (кэш из внешнего API + свои), приёмы пищи, дневные итоги КБЖУ
- Публикует: `food.meal_logged`, `food.daily_goal_reached`
- Реализовывать последним — по объёму работы сопоставим с остальными тремя модулями вместе

### 8.5 Motivation (не модуль, а слой)
- Не имеет своих данных verstoß — это подписчик на события всех остальных модулей
- Логика: XP, стрики, ачивки, уведомления о прогрессе
- Реализован как обработчики событий в `core` или как отдельный "виртуальный" модуль
  без собственных API-роутов, только с `events.py`

## 9. Фронтенд и PWA

- Роутинг с namespace на модуль: `/tasks/*`, `/habits/*`, `/finance/*`, `/food/*` —
  добавление модуля = новая ветка роутов + пункт меню в конфиге, без правки шелла
- **PWA через `vite-plugin-pwa`:**
  - `manifest.json` — иконка, имя приложения, `display: "standalone"` (убирает браузерный UI
    при добавлении на главный экран телефона)
  - Service Worker с кэшированием статики (JS/CSS/иконки) — для быстрой загрузки и частичной
    работы офлайн
  - API-запросы (TanStack Query) — офлайн-кэш последних данных, чтобы приложение открывалось
    даже при плохом интернете, с фоновой синхронизацией при восстановлении сети
- Mobile-first вёрстка на Tailwind — единый UI одинаково удобен на телефоне и десктопе без
  отдельного мобильного приложения

## 10. Безопасность и конвенции

- JWT в httpOnly cookies, bcrypt cost 12 — стандарт из твоих остальных проектов
- Деньги — всегда integer (копейки), никогда float — конвенция сохраняется и здесь,
  особенно важно, раз в системе будет модуль finance
- Rate limiting и security headers на Nginx — даже для личного проекта не лишнее,
  если сервер смотрит в интернет
- Разделение схем БД по модулям = естественная граница для бэкапов: можно бэкапить
  схему `finance` отдельно и чаще, чем, например, `habits`

## 11. Деплой

- Docker Compose: `backend`, `frontend` (сборка статики), `postgres`, `nginx`
- Nginx — TLS, раздача фронтенд-статики, прокси `/api/*` на FastAPI
- Единый `docker-compose.yml` для всего приложения — не нужно разносить модули по разным
  контейнерам, они живут в одном процессе FastAPI

## 12. Порядок реализации

1. **Core** — auth, event bus, module registry, общий shell на фронте (пустой, без модулей)
2. **Habits** — простейшая модель данных, первый рабочий модуль сквозь весь стек
3. **Tasks** — вторая проверка контракта модуля + первая межмодульная событийная связь
   (`habit.completed → task created`)
4. **Motivation** — слой поверх events от habits и tasks, первая "видимая" отдача
5. **Finance** — более сложная модель данных (категории, регулярные операции)
6. **Food** — последний, с MVP на ручном вводе продуктов, затем интеграция Open Food Facts

## 13. Расширение в будущем

Любое новое направление добавляется по контракту из раздела 5:
- новая папка в `backend/app/modules/`
- новая схема Postgres
- новая папка в `frontend/src/modules/`
- одна строка регистрации в `main.py` и одна — в конфиге меню фронтенда

Ядро, event bus и уже существующие модули не требуют изменений.
