# WORKFLOW.md — Спека-first + Test-first для модульного приложения

Этот документ описывает процесс, по которому каждый модуль (см. CLAUDE.md, раздел 8)
проходит путь от идеи до рабочего кода. Используется вместе с Claude Code: этот файл —
инструкция для сессии, `SPEC_TEMPLATE.md` — шаблон, `specs/{module}.md` — конкретные спеки.

## 1. Принцип

Два подхода совмещаются так, чтобы не дублировать работу:

**Спека — источник истины.** Она описывает *что* должно быть верно (данные, контракт API,
события, бизнес-правила), в том числе в форме Given/When/Then-сценариев.

**Тесты — механическая проекция спеки в код.** Каждый Given/When/Then-сценарий спеки
становится одним тестом (или несколькими). Тест не придумывает новое поведение — он
проверяет то, что уже написано в спеке.

Порядок работы над модулем всегда такой:

```
1. Спека (specs/{module}.md)         — пишется и утверждается ДО кода
2. Тесты (красные)                    — по каждому пункту "Критерии приёмки" из спеки
3. Реализация                         — минимум кода, чтобы тесты стали зелёными
4. Рефакторинг                        — тесты остаются зелёными
5. Сверка со спекой                   — все критерии приёмки отмечены как выполненные
6. Регистрация модуля                 — main.py + конфиг меню фронта (см. CLAUDE.md §5)
```

Если в процессе реализации выясняется, что спека неполна или неверна — **спека
правится первой**, затем тесты, затем код. Никогда не наоборот: код не должен молча
расходиться со спекой.

## 2. Структура файлов в репозитории

```
project/
  specs/
    _template.md          # копия SPEC_TEMPLATE.md
    habits.md
    tasks.md
    finance.md
    food.md
  backend/
    app/modules/habits/...
    tests/
      habits/
        test_service.py     # unit-тесты бизнес-логики (без БД, без HTTP)
        test_router.py       # API/integration-тесты (httpx AsyncClient + тестовая БД)
        test_events.py        # контрактные тесты: PUBLISHES/SUBSCRIBES_TO соответствуют спеке
      conftest.py            # общие фикстуры: тестовая БД, тестовый пользователь, event bus
  frontend/
    src/modules/habits/...
```

Тесты фронта — по желанию (Vitest + React Testing Library), но для личного проекта
приоритет отдаётся бэкенд-тестам: именно там живёт бизнес-логика и данные.

## 3. Уровни тестов на модуль

Для каждого модуля пишутся три вида тестов, в этом порядке:

1. **Unit (service.py)** — чистая бизнес-логика без БД и без HTTP. Например: расчёт
   стрика, расчёт КБЖУ, расчёт бюджета. Самые быстрые, пишутся первыми.
2. **Contract (events.py)** — проверка, что модуль публикует и подписывается ровно на то,
   что заявлено в спеке. Пример: "если `habits.PUBLISHES` содержит `habit.completed`,
   тест эмитит завершение привычки и проверяет, что событие реально ушло в шину с
   правильным payload".
3. **Integration/API (router.py)** — реальный HTTP-запрос через `httpx.AsyncClient` к
   поднятому FastAPI-приложению с тестовой Postgres-схемой модуля. Проверяет весь путь
   запрос → сервис → БД → ответ.

Строгий % покрытия не требуется (личный проект без внешних требований) — но каждый
пункт "Критерии приёмки" из спеки обязан иметь хотя бы один тест. Это и есть критерий
"готово".

## 4. Инструментарий

- `pytest` + `pytest-asyncio` (`asyncio_mode = auto` в `pyproject.toml`)
- `httpx.AsyncClient` с `ASGITransport` — для API-тестов без реального сетевого стека
- Тестовая БД: отдельная Postgres-схема с суффиксом `_test`, поднимается в `conftest.py`
  фикстурой с rollback после каждого теста (транзакция откатывается, не коммитится)
- Фикстуры пользователя/аутентификации — в `conftest.py` на уровне `backend/tests/`,
  переиспользуются всеми модулями
- `pytest-cov` — используется как индикатор пробелов, не как gate/порог для прохождения

## 5. Шаблон работы с Claude Code по одному модулю

Рекомендуемая последовательность промптов в Claude Code (по одному модулю за сессию):

1. **Дать контекст:** приложи `CLAUDE.md`, `WORKFLOW.md` и `specs/{module}.md`, попроси
   ничего не реализовывать, только пересказать своими словами контракт модуля — проверка,
   что спека понята правильно.
2. **Тесты first:** попроси написать все три уровня тестов (unit → contract → integration)
   строго по разделу "Критерии приёмки" спеки, без реализации самого модуля. Тесты должны
   падать (модуля ещё нет) — это ожидаемо.
3. **Ревью тестов:** просмотри тесты сам — они являются формальной проверкой того, что ты
   считаешь правильным поведением. Ошибка на этом шаге дешевле, чем ошибка в реализации.
4. **Реализация:** попроси реализовать модуль так, чтобы все тесты стали зелёными, без
   изменения самих тестов (если тест неверен — это отдельное решение, обсуждается явно).
5. **Рефакторинг:** отдельным шагом, с условием "тесты остаются зелёными".
6. **Регистрация:** роутер в `main.py`, пункт меню на фронте, коммит.

## 6. Definition of Done модуля

Модуль считается готовым, когда:
- [ ] Спека в `specs/{module}.md` утверждена (нет открытых вопросов)
- [ ] Каждый пункт "Критерии приёмки" покрыт минимум одним тестом
- [ ] Все тесты трёх уровней зелёные
- [ ] `events.py` модуля соответствует разделу "События" спеки дословно
- [ ] Модуль зарегистрирован в `main.py` и в конфиге меню фронта
- [ ] Схема Postgres модуля создана отдельной Alembic-веткой миграций
