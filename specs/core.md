# Спека модуля: core

> В отличие от остальных модулей, `core` не имеет `/api/{module_name}` в привычном
> смысле продуктовой фичи — это инфраструктура, от которой зависят все модули, но
> которая сама не знает об их существовании (см. CLAUDE.md §6). Реализуется первым.

## 1. Назначение

Единая аутентификация, событийная шина между модулями и реестр включённых модулей.

## 2. Границы (Scope)

**Входит в модуль:**
- JWT-аутентификация в httpOnly cookies (access + refresh)
- Событийная шина (async in-process pub/sub)
- Реестр модулей (статический конфиг: какие модули включены)

**Явно НЕ входит (Out of scope):**
- Публичная регистрация через API — пользователь создаётся один раз через CLI-скрипт,
  не через HTTP-эндпоинт (личное приложение, не нужен открытый в интернет `/register`)
- Ролевая модель/права доступа (пользователь один; если появится второй — на этом этапе
  различие ролей всё ещё не нужно, у обоих полный доступ к своим данным)
- OAuth/социальный вход
- Внешняя очередь событий (Redis и т.п.) — см. CLAUDE.md §7, добавляется отдельно, если
  понадобится персистентность/replay

## 3. Модель данных

Схема Postgres: `core`

### `core.user`

| Поле | Тип | Обязательное | Ограничения / примечания |
|---|---|---|---|
| id | UUID | да | PK |
| email | text | да | UNIQUE |
| password_hash | text | да | bcrypt, cost 12 |
| created_at | timestamptz | да | |

Таблица рассчитана на нескольких пользователей с самого начала (см. CLAUDE.md §6 —
"на случай, если позже подключишь второго пользователя"), хотя в MVP пользователь один.

### `core.refresh_token`

| Поле | Тип | Обязательное | Ограничения / примечания |
|---|---|---|---|
| id | UUID | да | PK |
| user_id | UUID | да | FK на `core.user` |
| token_hash | text | да | хэш токена, не сам токен |
| expires_at | timestamptz | да | |
| revoked_at | timestamptz | нет | заполняется при logout |
| created_at | timestamptz | да | |

Хранение refresh-токенов в БД (а не только в cookie) нужно для возможности отзыва
(logout инвалидирует конкретный токен, а не просто "забывает" его на клиенте).

## 4. API-контракт

| Метод | Путь | Запрос | Ответ | Коды |
|---|---|---|---|---|
| POST | /api/auth/login | `{email, password}` | `{user}` + cookies `access_token`, `refresh_token` (httpOnly, Secure, SameSite=Lax) | 200, 401 |
| POST | /api/auth/logout | — (по cookie) | — | 204 |
| POST | /api/auth/refresh | — (по cookie `refresh_token`) | новый `access_token` cookie | 200, 401 |
| GET | /api/auth/me | — (по cookie `access_token`) | `{id, email}` | 200, 401 |
| GET | /api/core/modules | — | `[{name, enabled}]` | 200 |

Регистрация пользователя — не HTTP-эндпоинт, а CLI-команда
(`python -m app.core.auth.create_user --email ... --password ...`), выполняемая один раз
при разворачивании.

## 5. Внутренний контракт: Event Bus

Не HTTP API — программный интерфейс, которым пользуются модули напрямую внутри процесса.

```python
class EventBus:
    def subscribe(self, event_name: str, handler: Callable[[dict], Awaitable[None]]): ...
    async def publish(self, event_name: str, payload: dict) -> None: ...
```

Гарантии, на которые опираются спеки остальных модулей (в частности `motivation.md` §6,
пункт про изоляцию ошибок):

- **Изоляция ошибок обработчиков.** Исключение в одном обработчике логируется, но не
  прерывает вызов остальных обработчиков того же события и не всплывает к вызвавшему
  `publish()`. Публикующий модуль не должен зависеть от того, упал ли подписчик.
- **Порядок вызова** — в порядке регистрации подписчиков (детерминированный, но не
  гарантирующий приоритет между модулями — порядок определяется порядком регистрации
  роутеров в `main.py`).
- **Синхронность в рамках запроса** — `publish()` дожидается завершения всех
  обработчиков (`await`) до возврата ответа клиенту; это осознанное упрощение MVP без
  фоновой очереди — если обработчик станет медленным, это будет видно как рост
  латентности исходного запроса, что и является сигналом к введению фоновой обработки.

## 6. Реестр модулей

Статический список в конфиге (`core/config.py`), не таблица БД на этом этапе.

**Важно:** `enabled` отражает факт, что роутер модуля реально примонтирован в
`main.py` — не намерение когда-нибудь его реализовать. На момент реализации самого
`core` ни один продуктовый модуль ещё не существует, поэтому на этом этапе все записи
должны быть `enabled: False`. Пример ниже — снимок состояния **после** того, как
`habits` и `tasks` уже зарегистрированы по шагу 5 (см. `PROMPTS.md`), а `finance` и
`food` — ещё нет:

```python
MODULES = [
    {"name": "habits", "enabled": True},
    {"name": "tasks", "enabled": True},
    {"name": "finance", "enabled": False},   # включается по мере реализации
    {"name": "food", "enabled": False},
]
```

Стартовая конфигурация на этапе реализации `core` — все четыре записи с `enabled: False`.

`GET /api/core/modules` отдаёт этот список фронтенду — конфиг меню на фронте фильтрует
пункты навигации по `enabled`, не имея собственного захардкоженного списка модулей.

## 7. Бизнес-правила и edge cases

- **Время жизни токенов:** access — 15 минут, refresh — 30 дней. Access никогда не
  хранится в БД (обычный подписанный JWT), refresh — хранится хэшированным для
  возможности отзыва.
- **Logout** помечает используемый `refresh_token` как `revoked_at`, обе cookie
  очищаются на клиенте.
- **Refresh с отозванным или истёкшим токеном** — 401, cookies очищаются.
- **`GET /api/core/modules`** не требует аутентификации (нужен на экране логина для
  построения навигации после входа) — но не отдаёт ничего чувствительного, только
  имена и статус включения.

## 8. Критерии приёмки

1. **Given** существующий пользователь, **When** POST `/login` с верными данными,
   **Then** 200, установлены cookies `access_token` и `refresh_token`, в БД создана
   запись `refresh_token`.
2. **Given** неверный пароль, **When** POST `/login`, **Then** 401, cookies не
   устанавливаются.
3. **Given** нет cookie, **When** GET `/api/auth/me`, **Then** 401.
4. **Given** валидный `access_token`, **When** GET `/api/auth/me`, **Then** 200 с
   данными пользователя.
5. **Given** истёкший `access_token`, но валидный `refresh_token`, **When** POST
   `/refresh`, **Then** 200, установлен новый `access_token`.
6. **Given** пользователь вызвал `/logout`, **When** POST `/refresh` тем же
   `refresh_token`, **Then** 401 (токен отмечен `revoked_at`).
7. **Given** два обработчика подписаны на одно событие, один из них выбрасывает
   исключение, **When** вызывается `bus.publish(...)`, **Then** второй обработчик всё
   равно выполняется, `publish()` не выбрасывает исключение наружу.
8. **Given** конфиг `MODULES` с `finance.enabled = False`, **When** GET
   `/api/core/modules`, **Then** в ответе `finance` присутствует с `enabled: false`.
