# Спека модуля: tasks

## 1. Назначение

Таск-трекер: создание и ведение задач с приоритетом, дедлайном и статусом; опциональная
автоматическая генерация задач по завершению привычек через подписку на события `habits`.

## 2. Границы (Scope)

**Входит в модуль:**
- CRUD задач (заголовок, описание, статус, дедлайн, приоритет, тег/проект-метка)
- Завершение и переоткрытие задачи
- Определение просроченных задач
- Настраиваемая связь "привычка → автосоздание задачи" (подписка на `habit.completed`)

**Явно НЕ входит (Out of scope):**
- Полноценные проекты с иерархией (в MVP — плоский текстовый тег, не отдельная сущность)
- Совместные задачи, назначение на других пользователей
- Повторяющиеся задачи (recurring) — это паттерн, уже решённый в `finance` для транзакций;
  если понадобится здесь — переиспользовать тот же подход отдельной итерацией

## 3. Модель данных

Схема Postgres: `tasks`

### `tasks.task`

| Поле | Тип | Обязательное | Ограничения / примечания |
|---|---|---|---|
| id | UUID | да | PK |
| user_id | UUID | да | FK на core.user |
| title | text | да | |
| description | text | нет | |
| status | enum: `todo`, `in_progress`, `done` | да | default `todo` |
| priority | enum: `low`, `medium`, `high` | да | default `medium` |
| tag | text | нет | свободный текст-метка, не отдельная сущность в MVP |
| due_date | date | нет | |
| created_at | timestamptz | да | |
| completed_at | timestamptz | нет | заполняется при переходе в `done` |

### `tasks.habit_task_link`

Конфигурация связи "привычка → задача" (позволяет включать/выключать автосоздание без
редактирования кода):

| Поле | Тип | Обязательное | Ограничения / примечания |
|---|---|---|---|
| id | UUID | да | PK |
| user_id | UUID | да | |
| habit_id | UUID | да | id привычки в модуле `habits` — **не FK**, модули не ссылаются друг на друга напрямую в БД, только по значению |
| task_title_template | text | да | например: "Внести вес" |
| enabled | boolean | да | default `true` |

## 4. API-контракт

| Метод | Путь | Запрос | Ответ | Коды |
|---|---|---|---|---|
| POST | /api/tasks | `{title, description?, priority?, due_date?, tag?}` | `Task` | 201, 422 |
| GET | /api/tasks | query: `status?, tag?, overdue_only?` | `Task[]` (с вычисленным `is_overdue`) | 200 |
| GET | /api/tasks/{id} | — | `Task` | 200, 404 |
| PATCH | /api/tasks/{id} | частичные поля | `Task` | 200, 404, 422 |
| POST | /api/tasks/{id}/complete | — | `Task` | 200, 404, 409 (уже завершена) |
| POST | /api/tasks/{id}/reopen | — | `Task` | 200, 404, 409 (не завершена) |
| DELETE | /api/tasks/{id} | — | — | 204, 404 |
| POST | /api/tasks/habit-links | `{habit_id, task_title_template}` | `HabitTaskLink` | 201, 422 |
| GET | /api/tasks/habit-links | — | `HabitTaskLink[]` | 200 |
| PATCH | /api/tasks/habit-links/{id} | `{enabled?, task_title_template?}` | `HabitTaskLink` | 200, 404 |
| DELETE | /api/tasks/habit-links/{id} | — | — | 204, 404 |

Доступ фильтруется по `user_id` из JWT, обращение к чужому ресурсу — 404.

## 5. События

**PUBLISHES:**

| Событие | Когда | Payload |
|---|---|---|
| `task.completed` | после успешного `POST /complete` | `{task_id, user_id, completed_at, priority}` |
| `task.overdue` | при обнаружении просроченной задачи (см. §6) | `{task_id, user_id, due_date}` |

**SUBSCRIBES_TO:**

| Событие | Источник | Обработчик делает |
|---|---|---|
| `habit.completed` | `habits` | Найти активный (`enabled = true`) `habit_task_link` по `habit_id` и `user_id` из payload; если найден — создать новую задачу с `title = task_title_template`, `priority = medium`, без `due_date` |

## 6. Бизнес-правила и edge cases

- **Обнаружение просрочки — лениво**, как и в `habits`: при каждом GET-запросе списка/
  детали задачи проверяется `due_date < сегодня AND status != done`; событие
  публикуется не чаще одного раза в календарный день на одну задачу (дедупликация по
  `task_id + date` в обработчике, не в БД) — повторные GET той же задачи в тот же день
  не публикуют `task.overdue` заново.
- **Автосоздание по привычке — идемпотентность:** если по одной и той же привычке в один
  день несколько раз происходит `habit.completed` (например, отметка снята и поставлена
  заново — событие публикуется каждый раз), создаётся задача каждый раз заново. Модуль
  `tasks` не дедуплицирует по дате — это осознанное упрощение MVP (пользователь сам
  удалит лишнюю задачу при необходимости); переоценить, если станет раздражать на практике.
- **`completed_at` при `reopen`:** сбрасывается в `NULL`.
- **Тег** — свободный текст без валидации набора значений в MVP; фильтрация по тегу —
  точное совпадение строки.

## 7. Критерии приёмки

1. **Given** нет задач, **When** POST `/api/tasks` с `{title: "Купить билеты"}`,
   **Then** возвращается 201 со статусом `todo` и приоритетом `medium` по умолчанию.
2. **Given** задача в статусе `todo`, **When** POST `/complete`, **Then** статус — `done`,
   `completed_at` заполнен, публикуется `task.completed`.
3. **Given** задача уже `done`, **When** повторный POST `/complete`, **Then** 409.
4. **Given** задача с `due_date` вчера и статусом `todo`, **When** GET списка задач,
   **Then** в ответе `is_overdue = true` и публикуется `task.overdue`.
5. **Given** задача с `due_date` вчера, **When** тот же GET списка выполняется повторно
   в тот же день, **Then** `task.overdue` не публикуется повторно.
6. **Given** активная связка `habit_task_link` для `habit_id = X` с шаблоном
   "Внести вес", **When** приходит событие `habit.completed` с `habit_id = X`,
   **Then** создаётся новая задача с `title = "Внести вес"`, `status = todo`.
7. **Given** связка для `habit_id = X` с `enabled = false`, **When** приходит
   `habit.completed` с `habit_id = X`, **Then** задача не создаётся.
8. **Given** нет связки для `habit_id = Y`, **When** приходит `habit.completed` с
   `habit_id = Y`, **Then** ничего не происходит, ошибок не возникает.
9. **Given** задача принадлежит другому пользователю, **When** GET `/api/tasks/{id}`,
   **Then** 404.

## 8. Нефункциональные заметки

- Объём данных небольшой, индексы по `(user_id, status)` и `(user_id, due_date)`
  достаточны для фильтрации.

## 9. Открытые вопросы

- Нужна ли многоуровневая структура проектов вместо плоского тега — отложено до
  накопления реального опыта использования.
- Стоит ли дедуплицировать автосоздание задач по привычке в пределах одного дня —
  переоценить после месяца использования.
