# Спека модуля: motivation

## 1. Назначение

Мотивационный слой поверх остальных модулей (см. CLAUDE.md §8.5): начисление опыта (XP),
уровней и ачивок на основе событий из `habits`, `tasks`, `finance`, `food`. Не имеет
собственных пользовательских данных вне своей учётной статистики — только подписки.

## 2. Границы (Scope)

**Входит в модуль:**
- Начисление XP за события из других модулей
- Расчёт уровня пользователя на основе накопленного XP
- Каталог достижений (ачивок) и их разблокировка по условиям
- Эндпоинт для фронтенда, отображающий текущий прогресс

**Явно НЕ входит (Out of scope):**
- Push/email-уведомления о достижениях (это UI/фронт, здесь — только событие)
- Соревновательные механики (лидерборды и т.п. — не нужны для одного пользователя)
- Настраиваемые пользователем правила начисления XP — в MVP правила зашиты в конфиг
  модуля, не редактируются через API

## 3. Модель данных

Схема Postgres: `motivation`

### `motivation.user_progress`

| Поле | Тип | Обязательное | Ограничения / примечания |
|---|---|---|---|
| user_id | UUID | да | PK, FK на core.user |
| xp_total | int | да | default 0 |
| level | int | да | default 1, производное от `xp_total`, но хранится денормализованно для быстрого чтения |
| updated_at | timestamptz | да | |

### `motivation.achievement` (статический каталог)

| Поле | Тип | Обязательное | Ограничения / примечания |
|---|---|---|---|
| code | text | да | PK, например `streak_7`, `streak_30`, `streak_100` |
| name | text | да | |
| description | text | да | |

**Источник истины для каталога — Python-константа** (`motivation/catalog.py`, список
словарей code/name/description), не сама таблица. Alembic-миграция модуля сидирует
таблицу из этой константы (idempotent insert, `ON CONFLICT (code) DO NOTHING`).
Тестовая фикстура сидирует ту же таблицу **из той же константы напрямую** (не полагаясь
на прогон миграции в тестовой схеме, если тестовая схема создаётся через
`metadata.create_all`, как в `habits`/`core`) — это исключает риск, что тестовый каталог
разойдётся с продакшен-каталогом.

### `motivation.user_achievement`

| Поле | Тип | Обязательное | Ограничения / примечания |
|---|---|---|---|
| user_id | UUID | да | |
| achievement_code | text | да | FK на `motivation.achievement.code` |
| unlocked_at | timestamptz | да | |
| | | | PK(user_id, achievement_code) |

## 4. API-контракт

Модуль не предоставляет мутирующих эндпоинтов пользователю (XP и ачивки начисляются
только через события) — только чтение для фронтенда:

| Метод | Путь | Запрос | Ответ | Коды |
|---|---|---|---|---|
| GET | /api/motivation/summary | — | `{xp_total, level, xp_to_next_level, recent_achievements}` | 200 |
| GET | /api/motivation/achievements | — | `Achievement[]` (с флагом `unlocked` и `unlocked_at`) | 200 |

- **`xp_to_next_level`** — вычисляется на лету в сервисе, не хранится:
  `100 - (xp_total % 100)`.
- **`recent_achievements`** — последние 5 разблокированных ачивок пользователя,
  отсортированные по `unlocked_at DESC`.

## 5. События

**PUBLISHES:**

| Событие | Когда | Payload |
|---|---|---|
| `motivation.xp_awarded` | при начислении XP за любое входящее событие | `{user_id, amount, reason}` |
| `motivation.level_up` | когда `xp_total` пересекает порог следующего уровня | `{user_id, new_level}` |
| `motivation.achievement_unlocked` | при выполнении условия ачивки | `{user_id, achievement_code}` |

**SUBSCRIBES_TO:**

| Событие | Источник | Обработчик делает |
|---|---|---|
| `habit.completed` | `habits` | +10 XP; если `current_streak` из payload достигает порога ачивки (7, 30, 100) — разблокировать соответствующую (`streak_7`/`streak_30`/`streak_100`) |
| `habit.streak_broken` | `habits` | не начисляет XP; используется только как источник данных для будущих "анти-ачивок" (в MVP — no-op, но подписка объявлена явно) |
| `task.completed` | `tasks` | +5 XP при `priority: low/medium`, +10 XP при `priority: high` |
| `food.daily_goal_reached` | `food` | +15 XP; отслеживать количество раз для будущей ачивки "7 дней подряд в цели" (в MVP — только XP, счётчик подряд идущих дней — открытый вопрос, см. §9) |
| `finance.budget_exceeded` | `finance` | XP не начисляется — это событие вне позитивной механики; в MVP no-op, зарезервировано под будущую "мягкую" обратную связь в UI |

## 6. Бизнес-правила и edge cases

- **Идемпотентность начисления:** мотивационный слой доверяет входящим событиям как
  есть — если модуль-источник публикует событие повторно за одно и то же действие
  (например, `habit.completed` при повторном checkin/uncheckin/checkin в один день, см.
  `tasks.md` §6 про аналогичный случай), XP начисляется повторно. Это осознанное
  упрощение MVP: `motivation` не хранит идентификаторы уже обработанных событий.
- **Расчёт уровня:** `level = xp_total // 100 + 1` (каждые 100 XP — новый уровень) —
  простая формула для MVP, зафиксирована как конфигурационная константа, а не хардкод
  в нескольких местах.
- **Атомарность `xp_total`/`level`:** оба поля обновляются одним `UPDATE`-запросом внутри
  одной БД-транзакции — новый уровень вычисляется в коде до записи и пишется вместе с
  новым `xp_total`. Не существует пути кода, который обновил бы одно поле без другого;
  рассогласованное промежуточное состояние невозможно по конструкции.
- **Разблокировка ачивки — один раз:** повторное выполнение условия (например, ещё один
  7-дневный стрик после разблокировки `streak_7`) не создаёт вторую запись и не
  публикует событие повторно — проверка на существование `user_achievement` перед
  вставкой.
- **Порядок обработки событий:** обработчики `motivation` не должны падать и ронять
  публикацию события в модуле-источнике — любая ошибка в обработчике логируется, но не
  прерывает основной поток (транзакция модуля-источника не должна зависеть от
  motivation).

## 7. Критерии приёмки

1. **Given** `xp_total = 0`, **When** приходит `habit.completed`, **Then** `xp_total`
   становится 10, публикуется `motivation.xp_awarded` с `amount: 10, reason: "habit_completed"`.
2. **Given** `xp_total = 95`, **When** приходит событие, добавляющее 10 XP,
   **Then** `xp_total = 105`, `level` меняется с 1 на 2, публикуется `motivation.level_up`.
3. **Given** нет разблокированной ачивки `streak_7`, **When** приходит `habit.completed`
   с `current_streak: 7`, **Then** создаётся `user_achievement(streak_7)`, публикуется
   `motivation.achievement_unlocked`.
4. **Given** ачивка `streak_7` уже разблокирована, **When** снова приходит
   `habit.completed` с `current_streak: 7` (другая привычка), **Then** вторая запись не
   создаётся, событие повторно не публикуется.
5. **Given** приходит `task.completed` с `priority: high`, **Then** начисляется 10 XP;
   **Given** `priority: low`, **Then** начисляется 5 XP.
6. **Given** приходит `finance.budget_exceeded`, **When** обработчик срабатывает,
   **Then** `xp_total` не меняется (no-op в MVP).
7. **Given** обработчик `motivation` на `habit.completed` падает с исключением, **When**
   `habits` публикует это событие, **Then** сама операция в `habits` (создание checkin)
   не откатывается и не завершается ошибкой.

## 8. Нефункциональные заметки

- Объём данных минимальный (одна строка `user_progress`, десятки ачивок) —
  производительность не является фактором.

## 9. Открытые вопросы

- Нужен ли счётчик "N дней подряд с достигнутой целью по калориям" для будущей ачивки —
  потребует либо хранения истории в самом `motivation`, либо более богатого payload от
  `food`; отложено.
- Стоит ли вводить дедупликацию начисления XP по идентификатору события (если модули
  начнут генерировать дубликаты чаще, чем ожидалось) — переоценить по факту использования.
- Ачивки по количеству (например, "100 выполненных задач"), а не по стрику — в MVP не
  реализованы: потребуют отдельного персистентного счётчика (стрик уже приходит готовым
  в payload `habit.completed`, а количество задач — нет, его пришлось бы накапливать в
  `motivation` самостоятельно). Раньше в примерах кода ачивок ошибочно фигурировал
  `tasks_100` — убран из §3 до появления реальной механики.
