# PROMPTS.md — готовые промпты для Claude Code

Шаблоны под семь шагов из `WORKFLOW.md` §6. Подставляй `{module}` (например, `habits`)
и путь до спеки. Прикладывай к каждому промпту файлы, указанные в скобках после
заголовка шага. Порядок модулей — по CLAUDE.md §12: `core` → `habits` → `tasks` →
`motivation` → `finance` → `food`. Фронтенд теперь делается сразу после бэкенда одного
модуля (шаги 6–7), а не отдельным проходом по всем модулям в конце.

---

## Шаг 0 — старт нового модуля (разово, до первого промпта)

Прикладываешь: `CLAUDE.md`, `WORKFLOW.md`, `specs/{module}.md`

```
Мы начинаем реализацию модуля `{module}` в проекте, описанном в CLAUDE.md.
Процесс работы описан в WORKFLOW.md — работаем по нему строго, шаг за шагом,
не забегай вперёд и не пиши код реализации, пока я явно не попрошу об этом.

Спека модуля — specs/{module}.md.

Сначала: перескажи своими словами контракт модуля — данные, API, события
(что публикует и на что подписан), ключевые бизнес-правила. Ничего не реализуй.
Если в спеке есть противоречие или неясность — прямо укажи на это, не додумывай
за меня.
```

Дальше — читаешь пересказ, поправляешь спеку при необходимости (см. WORKFLOW.md §1:
спека правится первой), и только потом переходишь к шагу 1.

---

## Шаг 1 — тесты first (прикладываешь: те же файлы + пересказ уже не нужен)

```
Контракт модуля подтверждён. Переходим к шагу 2 из WORKFLOW.md.

Напиши тесты для модуля `{module}` по разделу "Критерии приёмки" specs/{module}.md —
каждый пункт Given/When/Then должен стать минимум одним тестом. Три уровня, в этом
порядке:

1. Unit-тесты бизнес-логики в tests/{module}/test_service.py — без БД, без HTTP
2. Контрактные тесты событий в tests/{module}/test_events.py — проверяют, что модуль
   публикует и подписывается ровно на события, перечисленные в разделе "События" спеки
3. Интеграционные тесты API в tests/{module}/test_router.py — через httpx.AsyncClient
   и тестовую схему Postgres (используй фикстуры из tests/conftest.py, не создавай новые
   без необходимости)

Самого модуля {module} ещё не существует — тесты должны падать при запуске, это
ожидаемо. НЕ пиши реализацию на этом шаге, только тесты.

После — покажи, как тесты соотносятся с пунктами "Критерии приёмки": если какой-то
пункт спеки не покрыт ни одним тестом, укажи это явно, а не пропускай молча.
```

---

## Шаг 2 — ревью тестов (это делаешь ты сам, не Claude Code)

Не промпт, а чеклист перед тем, как двигаться дальше:
- [ ] Каждый пункт "Критерии приёмки" спеки покрыт минимум одним тестом
- [ ] Тесты действительно проверяют поведение из спеки, а не то, что "показалось
      естественным" во время написания
- [ ] Тесты падают по правильной причине (модуля нет), а не из-за ошибки в самих
      тестах — стоит быстро прогнать и посмотреть на трейсбек

Если что-то не так — правишь тесты или возвращаешься к спеке, только после этого
переходишь к шагу 3.

## Шаг 3 — реализация

```
Тесты написаны и подтверждены. Переходим к шагу 3 из WORKFLOW.md.

Реализуй модуль `{module}` (router.py, models.py, schemas.py, service.py, events.py,
Alembic-миграция для схемы `{module}`) так, чтобы все тесты из
tests/{module}/test_service.py, test_events.py и test_router.py стали зелёными.

Не изменяй сами тесты. Если при реализации выяснится, что какой-то тест написан
неверно или противоречит спеке — останови реализацию и опиши мне расхождение,
не исправляй тест самостоятельно молча.

Следуй контракту модуля из CLAUDE.md §5: APIRouter с префиксом /api/{module}, модели
со схемой {module}, events.py с явными списками PUBLISHES и SUBSCRIBES_TO.
```

## Шаг 4 — рефакторинг

```
Все тесты модуля {module} зелёные. Переходим к шагу 4 из WORKFLOW.md.

Проведи рефакторинг реализации модуля {module}: убери дублирование, вынеси повторяющуюся
логику, улучши читаемость. Условие: после каждого изменения все тесты
tests/{module}/ остаются зелёными. Если какой-то рефакторинг требует изменения теста —
останови и спроси, не меняй тесты по своей инициативе.
```

## Шаг 5 — регистрация бэкенда

```
Модуль {module} реализован и отрефакторен, тесты зелёные. Переходим к шагу 6 из
WORKFLOW.md (регистрация бэкенда).

1. Зарегистрируй router модуля {module} в backend/app/main.py
2. Добавь модуль в MODULES в core/config.py (или включи enabled: true, если уже
   присутствует) — см. specs/core.md §6
3. Прогони весь набор тестов проекта (не только модуля {module}) — убедись, что
   регистрация не сломала другие модули через event bus

Пункт меню фронтенда сюда не входит — это отдельный шаг (см. Шаг 7 ниже).
Не редактируй код ядра (core/auth, core/events) и код уже существующих модулей, кроме
точек регистрации, перечисленных выше.
```

## Шаг 6 — бутстрап фронтенда (разово, только перед фронтендом `core`)

Прикладываешь: `CLAUDE.md`, `WORKFLOW.md`, `DESIGN_SYSTEM.md`

```
Бэкенд core и habits уже реализован и зарегистрирован. Начинаем фронтенд — сначала
разовый бутстрап проекта, описанный в WORKFLOW.md §5.

Создай frontend/ по структуре из CLAUDE.md §4:
- Vite + React + TypeScript
- Tailwind CSS + shadcn/ui (инициализация)
- motion/react — для анимаций, lucide-react — для иконок
- Импорт шрифта Inter (300–700) и токены из DESIGN_SYSTEM.md §2 (--font-sans,
  --color-brand-gray) — применяются вместо дефолтной темы shadcn
- TanStack Query: QueryClientProvider в корне приложения
- Роутер (React Router) с корневым layout'ом из core/shell
- vite-plugin-pwa: manifest.json, display: "standalone", кэширование статики
- core/api-client.ts — обёртка над fetch с credentials: 'include' (обязательно для
  httpOnly cookie-сессии) и базовым URL на backend

Модулей ещё нет — на этом шаге создаётся только каркас и core/shell (пустой layout без
пунктов меню, они появятся по мере регистрации модулей).
```

## Шаг 7 — фронтенд `core`: экран логина

Прикладываешь: `CLAUDE.md`, `specs/core.md`, `DESIGN_SYSTEM.md`

```

целиком: без полей имени/фамилии, без Google/Github, без разделителя "Or", без ссылки

Прикладываешь: `CLAUDE.md`, `WORKFLOW.md`, `specs/{module}.md`, `DESIGN_SYSTEM.md`

```
Бэкенд модуля {module} зарегистрирован. Переходим к шагу 7 из WORKFLOW.md — фронтенд.

Реализуй фронтенд-часть модуля {module} по разделу "API-контракт" specs/{module}.md —

порядок сортировки, что именно показывать при пустом списке) — предложи разумный
вариант и явно скажи, что это твоё предположение, а не выведи молча.

## Примечание к модулю `core`

`core` реализуется первым и не проходит по этому шаблону один в один — у него нет
"критериев приёмки" в смысле пользовательских сценариев одного модуля, а есть
инфраструктурные гарантии (см. `specs/core.md` §8). Шаги 0–4 применяются к нему так же
(спека → тесты → реализация → рефакторинг), шаг 5 (регистрация) для `core` не нужен —
он сам является точкой регистрации для всех остальных. Фронтенд `core` (шаги 6–7) —
не отдельный модульный экран, а инфраструктура: логин-форма по `DESIGN_SYSTEM.md` §6,
`ProtectedRoute`, shell с навигацией (см. WORKFLOW.md §5).

## Примечание к модулю `motivation`

`motivation` не имеет мутирующих API-эндпоинтов (см. `specs/motivation.md` §4) — на
шаге 3 акцент делается на `events.py` (подписки) и расчётной логике в `service.py`,
`router.py` содержит только два `GET`-эндпоинта для фронтенда. На шаге 7 фронтенд тоже
только читающий — сводка XP/уровня/ачивок без форм редактирования.
